This is an EmDash site — a CMS built on Astro with a full admin UI — for **Minna hoitaa**, a pet care / home cleaning / garden maintenance business. Build plan and content spec: [PLAN.md](PLAN.md). Progress against the plan's phases is tracked in the session's task list, not in this file.

## Commands

```bash
pnpm dev              # Start dev server (runs migrations, seeds, generates types) + EmDash admin
npx emdash types      # Regenerate TypeScript types from schema
pnpm approve-builds --all   # Needed once after install (parcel/watcher build script)
```

The admin UI is at `http://localhost:4321/_emdash/admin`.

**Node caveat:** EmDash's docs state odd-numbered Node majors are unsupported. If the environment's global Node is odd (currently v25 here), use the pinned Node 22 install instead — see [README.md](README.md#prerequisites) for the exact PATH prefix.

## Rules

**EmDash-specific:**
- All content pages must be server-rendered (`output: "server"`). No `getStaticPaths()` for CMS content.
- Image fields are objects (`{ src, alt }`), not strings. Use `<Image image={...} />` from `"emdash/ui"`.
- `entry.id` is the slug (for URLs). `entry.data.id` is the database ULID (for API calls like `getEntryTerms`).
- Always call `Astro.cache.set(cacheHint)` on pages that query content.
- Taxonomy names in queries must match the seed's `"name"` field exactly (e.g., `"category"` not `"categories"`).
- Content is Portable Text (structured JSON) — render with `<PortableText>`, never `set:html`.
- `getSiteSettings()`'s built-in schema is fixed (`title`, `tagline`, `logo`, `favicon`, `url`, `postsPerPage`, `dateFormat`, `timezone`, `social`, `seo`) — it cannot be extended with custom fields. Business data the plan calls "site settings" (phone, email, WhatsApp, Y-tunnus, service area) needs its own singleton collection instead; `social.facebook` does cover the Facebook URL.

**Project-specific (see PLAN.md for full rationale):**
- No inline `style="…"` attributes anywhere. No Tailwind. No `!important`.
- BEM everywhere in component markup and SCSS (`.service-card`, `.service-card__icon`, `.service-card--pets`).
- Every CTA resolves to `CONTACT_PATH` from `src/lib/routes.ts` — never a hardcoded path. In page content that means `@contact` as the block's CTA URL, not `/ota-yhteytta/`. Block link URLs are also filtered by `links.ts` (`resolveHref`): only relative paths, `#`/`?` fragments and `http(s):`/`mailto:`/`tel:` render; `javascript:`, `data:` and `//host` links are dropped.
- Progressive enhancement only: the site must be fully readable/navigable with JS disabled.

## This project's content model

Not the generic starter's blog schema — built per [PLAN.md §4](PLAN.md): `pages` and `business_info` (a one-entry collection — EmDash has no dedicated singleton type, "one entry by convention" is the pattern). The starter's `posts`/`category`/`tag` collections and routes have been removed — they weren't part of this site's IA.

`pages` is genuinely slug-routed (added 2026-07-31, reversing an earlier decision): `src/pages/[...slug].astro` + `src/pages/en/[...slug].astro` render any published `pages` entry via the shared `src/components/pages/GenericPage.astro` (title + Portable Text `content`, `PageLayout`, 404 = route files set `Astro.response.status = 404` and `GenericPage` renders an inline `NotFoundPage`, rather than a redirect/rewrite — keeps the locale that was already resolved from the real request URL instead of re-deriving it from a rewritten path). **Creating pages needs no code changes.** Two things make the admin's links land on the catch-all instead of a 404: (1) the `pages` collection has `urlPattern: "/{slug}"` (admin's "view on site" link otherwise defaults to `/pages/<slug>`) — in `seed/seed.json` *and* set on an existing DB via `PUT /_emdash/api/schema/collections/pages`, since seed changes don't re-apply to a populated DB; (2) draft previews use `EMDASH_PREVIEW_PATH_PATTERN` (default `/{collection}/{id}` → `/pages/<id>`), set to `/{locale}/{id}` through `vite.define` in `astro.config.mjs`, and the catch-all resolves an entry by id as well as slug. The admin's link never carries a locale prefix, so `src/lib/pages.ts` redirects a default-locale slug that exists only in another locale (e.g. an English-only page) to its `/en/…` URL. Pages appear at `/{slug}` (fi) and `/en/{slug}`; they are *not* added to the nav menus automatically — add menu items in the admin.

**Homepage as blocks (step 2 of the migration, done): `/` and `/en/` render the `etusivu` entry** (`/etusivu` and `/en/etusivu` 301 to them) — 8 Portable Text blocks reproducing the current homepage: `marketing.hero` (Joku on kotona, portrait area with lamp glow) → `marketing.features` (Palvelut, 3 linked cards with the pets/cleaning/garden icons) → plain `h2` + paragraphs (Minusta) → `marketing.testimonials` → `marketing.hero` (centered + dark = the ContactBand look). Measured against `/` in the browser at 1280 and 375 px: section heights, card sizes, heading sizes/alignment match (within ~4 px). Content lives in `seed/seed.json` *and* was written to the live DB via the admin API. The old `HomePage.astro`, `Hero.astro`, `ServiceCard.astro`, `TestimonialStrip.astro` and the now-unused `home.*`/`cta.readMore*` i18n keys were deleted (git history has them); the `koti-hero` and `minusta` (`about-me` in en) entries were deleted. Things to know:
- Content lives in the page blocks, not in collections: the `services`, `testimonials`, `price_groups`, `price_items` and `gallery_items` collections were all deleted as their pages became blocks (the homepage's testimonials block and the Features/Hero blocks hold the text). What remains as collections: `pages`, `business_info`.
- `GenericPage` layout model: every `marketing.*` block owns its section/background/container (a dark band must be full-bleed, so blocks are *not* wrapped in a shared `.l-container`); consecutive plain blocks are grouped into a prose column (`44rem`), rendered as a white `.l-section` band when it sits after/between blocks and as a plain column when it directly follows the page-title header.
- Heading level: Hero renders the tag straight from its `headingLevel` field (h1 default | h2). If the content's first block is a `marketing.hero` at h1, that hero is the page `<h1>` (page-opening spacing + staggered reveal) and `GenericPage` skips the `PageLayout` title header. `GenericPage` rewrites `headingLevel` to `"h2"` on every *other* hero before rendering, so a page always has exactly one `<h1>` and no duplicate title.
- Hero block fields: `centered`, `dark` (full-bleed dark band, reads like the former `ContactBand`), `white` (full-bleed white band, `--c-white`; ignored if `dark` is on), `showImage` (media area — with the glow, or the icon glyph, when there's no image) + `imageUrl` (a `media_picker` element: opens the media library, stores only the picked file's URL) / `imageAlt`. Features: per-card `linkUrl`/`linkLabel`. Feature icons include `pets`/`cleaning`/`garden`, drawn by the host's `ServiceIcon.astro` (same glyphs as the services pages).
- (History) the old homepage's hero CTA never got its intended `margin-top: var(--s-7)`: `.hero__cta` is set on `<Button>`'s root from the parent's scoped CSS, which Astro scoping doesn't reach — so on `/` the button touches the paragraph. The block implements the intended 32 px gap, so the live homepage now has it.
- (History) the old `/en/` homepage had no "About me" section (it looks up the slug `minusta` in `en`, where the entry is `about-me`); the block-based `/en/` includes it.
- **Dev-server quirk**: CSS for the linked `packages/marketing-blocks` components (and sometimes `GenericPage`) can go stale in the running dev server after edits (templates update, the JS-wrapped style module doesn't). `touch` the edited files, or restart. Changes to the plugin's `admin.portableTextBlocks` (`packages/marketing-blocks/src/index.ts`) need a restart to reach the admin UI.

**Pricing page as blocks (step 3): `/hinnasto/` and `/en/hinnasto/` render the `hinnasto` entry** — plain H2 ("Lemmikin hoito" / "Kodin siivous ja puutarhanhoito") + EmDash's *built-in* `table` block (editor `/table`; there is no custom table block in the marketing plugin) + plain paragraphs + a closing dark centered `marketing.hero` (the former ContactBand). Tables are rendered by `src/components/SiteTable.astro`, registered as the `type.table` override in `GenericPage`; it reproduces the old PriceTable look (measured identical row height/fonts/border at 1280 and 375 px): borderless, one hairline per row, first column = row label (semibold), other columns right-aligned small muted print, and **bold text in a cell = the price** (display font, spruce, larger) — that is the editor convention for price cells. The `price_items` content type, the `PriceTable`/`PricingPage` components and their route files were deleted; `price_groups` is now unused but still exists. The page is ~80 px shorter than before: the old terms block had a top rule + large gap, now it's a plain paragraph after the table.

**Services page as blocks (step 4): `/palvelut/` and `/en/palvelut/` render the `palvelut` entry** — `break` (EmDash's built-in Divider) + `marketing.hero` ×3 (wide media shape, alternating `mediaLeft`, icon chip + glyph, body paragraphs, bullet list, `anchor` = the old `#lemmikkihoito`/`#pet-care` ids the homepage cards link to) + a closing dark centered CTA hero. Measured against the old page at 1280/375 px: identical total height (2853/4105 px), media 568×568 in the same alternating positions. The `services` collection, `ServicesPage`, `ServiceSection`, `ContactBand`, the `/palvelut` route files and the JSON-LD `makesOffer` (which read the collection; `LocalBusiness` JSON-LD itself stays: name, phone, email, area, price range) were removed; `testimonials.service` (a reference to `services`) was removed too.
- **Hero block additions**: `headingLevel` (h1 default | h2), `icon` (same picker as Features; also drawn as a big glyph in the media area when there's no image), `list` (repeater, one `text` per row — same shape as the old `services.bullets`), body text = the multiline field split into paragraphs, `mediaShape` (`portrait` hero look with lead-size muted text | `wide` section look with body-size text), `mediaLeft`, `anchor` (renders `id`).
- **Hero image**: the picked image is rendered (emdash/ui `Image` with the URL string → a plain `<img>` with the given alt, no srcset) *inside* `.marketing-hero__media`, absolutely positioned to fill it with `object-fit: cover` (no glow when an image is set: `.marketing-hero__glow` is only the placeholder for a missing picture, rendered when there's neither an image nor an icon glyph — the glyph carries its own glow) — deliberately an `<img>`, not a CSS `background-image`: it carries real alt text, and a per-instance background would need an inline `style` (banned here). The media box now has an explicit shape so there's always something to fill: `portrait` = 4:5, `wide` = 1:1 (the size the old services glyph area actually had — its SVG was stretched to the whole box because Astro's scoping doesn't reach the child component's `<svg>`, so the intended 5rem glyph size never applied; the block reproduces that, so the icon glyph fallback is currently huge, 568 px).
- **Catch-all housekeeping**: paths that look like files (`/wp-login.php`, `/apple-touch-icon.png` — `looksLikeFile` in `src/lib/pages.ts`) get a bare `404` from the route without any lookup or full-page render; `business_info` is fetched once per request via `getBusinessInfo(Astro.locals, locale)` (`src/lib/business-info.ts`), shared by `BaseLayout` (JSON-LD) and the Contact block.
- **One `<h1>` rule** (in `GenericPage`): only the *first* block, if it's a hero left at level h1, is the page `<h1>` (and replaces the title header); every other hero renders `<h2>` even if h1 was picked.
- **Dividers**: EmDash's `break` block is overridden by `SiteBreak.astro`; a run consisting only of dividers is drawn as a bare full-width hairline (`.generic-divider`) between section blocks, not as a padded prose band. Runs of only empty paragraphs (the editor's trailing paragraph) are dropped.
- **Dev-server gotcha (seed cache)**: the running dev server holds the seed from *startup* (virtual module) and `dev-bypass` re-applies it on every call. After deleting a collection/entry that is still in the startup seed, the next `dev-bypass` brings the collection back (or fails with `UNIQUE constraint failed: ec_pages.slug, ec_pages.locale` for trashed pages — soft-deleted rows keep the slug reserved). Edit `seed.json`, restart the server, *then* delete from the DB — and purge trashed pages (`DELETE …/content/pages/{id}/permanent`) whose slugs are reused.

**Privacy page (step 5): `/tietosuoja/` and `/en/tietosuoja/` need no template.** The dedicated `PrivacyPage` and its routes were deleted; `GenericPage` renders the `tietosuoja` entry (measured against the old page at 1280/375 px in both locales: identical heading sizes, spacing and total height; only the column moved). By client decision the text is then left-aligned with the page title (a full-width flow with a 44rem measure for paragraphs/lists, `generic-page--first`) rather than the old centered column — the same flow the pricing tables use. Prose *between/after blocks* is still the centered 44rem white band.

**Contact page (step 6): `/ota-yhteytta/` and `/en/ota-yhteytta/` render the `ota-yhteytta` entry**, whose content is a single `marketing.contact` block — left column: the company details read live from the `business_info` collection (phone/e-mail/WhatsApp/service area/Y-tunnus, so a changed number updates everywhere), right column: an editor-set heading + one of the site's forms (`ContactForm.astro`, now taking an optional `formId`). Measured against the old `ContactPage` at 1280/375 px: identical positions/sizes, page height 1206/1944 px. Details worth knowing:
- Block fields: `note` (lead-in text above the details, was the i18n `contact.responseTime`), `formHeading` (was `contact.formHeading`), `formId` (optional; **empty = the per-locale form** `yhteydenotto`/`contact`). It is a plain text field, not a dropdown: EmDash's dynamic select (`optionsRoute`) only calls a route of the *declaring* plugin, and a plugin can't read another plugin's (forms) storage — a proxy route would have to self-fetch the forms plugin's admin route with the editor's cookies, which is fragile on Workers.
- The block is deliberately coupled to the host site (like Hero's `Button`): it reuses `ContactForm.astro` (theming, accessible error summary, privacy-statement link), the `contact.*Label` i18n keys and `formatPhoneDisplay`; locale comes from `Astro.currentLocale`. Its padding is bottom-only — it's meant to sit right under the page title header.
- New optional **`pages.intro`** field ("Ingressi"): shown by `GenericPage` under the H1 via `PageLayout`'s `intro` (fs-500, muted) — the contact page uses it for the old intro sentence. Added to `seed.json` and to the live DB with `POST /_emdash/api/schema/collections/pages/fields`. Not shown on pages that open with a hero (they have no title header).
- `ContactPage`, its route files and the i18n keys `contact.intro`/`responseTime`/`formHeading`/`pages.contactHeading` were removed; `business_info` is still read by the block and by the JSON-LD in `BaseLayout`.

**Gallery page (step 7): `/galleria/` and `/en/galleria/` render the `galleria` entry** — no gallery block or content type: the page content is 26 EmDash built-in `image` blocks (media-library picker, alt text and caption per image, drag-to-reorder in the editor, all via `/image`). `GenericPage` merges **2+ consecutive `image` blocks** into one synthetic `{_type: "gallery", images}` node (same shape as EmDash's own gallery block) rendered by `SiteGallery.astro` (registered as the `type.gallery` override): 2 columns on mobile, 3 from md, square crops, rounded corners, optional caption; a lone image stays an ordinary image, and a gallery right under the title header has no extra spacing. Measured identical to the old page at 1280/375 px (same 26 tiles, 381/160 px squares, page height 3965/2670 px). Why not a Block Kit gallery block: the plugin `media_picker` element stores only the file URL (no media id/width/height/blurhash → no layout-shift-free optimized images, alt typed separately) and isn't allowed inside `repeater` sub-fields (text/number/select/toggle only). `scripts/populate-gallery.py` (fi/en alt texts live in it) now replaces the `galleria` pages' content with the image blocks — idempotent, re-running discards manual edits to that content; images are excluded from `seed.json` because media ids are per-DB. The `gallery_items` collection, `GalleryPage`, `GalleryGrid` and the `/galleria` route files were deleted.

**Page entries for the main routes (step 1 of a planned migration)**: `pages` now also has entries (fi + en, published, title only, no content) with slugs `etusivu`, `palvelut`, `hinnasto`, `galleria`, `ota-yhteytta`, in `seed/seed.json` and the live dev DB. They are **not used yet**: `/palvelut/` etc. are still served by their dedicated templates (static routes beat the catch-all), and only `/etusivu` (which has no static route — the homepage is `/`) actually renders the entry, as a bare title. The plan is to move each template's content into Portable Text blocks on these entries later; until then don't treat the entries' emptiness as a bug.

Astro prioritizes static/index routes over this catch-all, and there are no dedicated page routes left: every public page (`/`, `/palvelut/`, `/hinnasto/`, `/galleria/`, `/tietosuoja/`, `/ota-yhteytta/`) is a `pages` entry rendered by it (only `404.astro` and the catch-alls remain in `src/pages/`). The former text fragments `koti-hero`, `minusta` (homepage) and `hinnasto-ehdot`/`pricing-terms` (pricing terms) were deleted once their pages became blocks / plain body text. (Sections were considered and rejected for fragments: no `locale`/`translationOf` field, and no draft/publish status — a real downgrade from what `pages` gives editors today.)

**SEO plumbing**: `pages` has `supports: [..., "seo"]` (admin SEO panel: title, description, canonical, noindex; on an existing DB set with `PUT /_emdash/api/schema/collections/pages {"hasSeo":true}`). `BaseLayout` emits a self-referencing canonical (no trailing slash, except `/` and `/en/`; origin = `Astro.site` or the request origin, so no `site` config is needed) and hreflang + `x-default` from EmDash's `getHreflangAlternates` (translation-group aware; the `etusivu` entry's `/etusivu` URLs are mapped to `/` by `src/lib/seo.ts`). `GenericPage` precedence: SEO panel > route default > entry title/`intro`. 404s are `noindex`. `src/pages/sitemap-pages.xml.ts` replaces EmDash's generated pages sitemap (which listed the homepage as `/etusivu`); per-entry SEO is only present on the single-entry query, hence one `getEmDashEntry` per entry there. Per-page titles/descriptions are seeded by `scripts/set-page-seo.py` (the seed format can't carry them); the homepage title comes from `pages.homeTitle`. The same script uploads `content-source/og-image.jpg` (1200×630 crop of the homepage hero photo, gitignored) and sets it as the site-wide default share image (`settings.seo.defaultOgImage` → `og:image`, `twitter:card=summary_large_image`).

**Structured data & GEO**: `BaseLayout` emits a `LocalBusiness` node (`@id` = `<origin>/#business`, `areaServed` = the four capital-region cities from `SERVICE_AREA_CITIES` in `src/lib/seo.ts`, `priceRange` from `business_info.price_range`, `taxID`, `sameAs` = the Facebook URL from site settings, `image` = default OG image) and any page-level nodes passed as `jsonLd` (always serialised through `ldJson()`, which escapes `<`). `src/lib/structured-data.ts` derives those nodes from a page's blocks in `GenericPage`: `BreadcrumbList` (every page but the homepage), `FAQPage` from any `marketing.faq` block, `Service` per `marketing.hero` with an `anchor` on the `palvelut` page, and an `OfferCatalog` from `table` blocks (rows with a bold `18 €` / `€18` price cell; the row label + the preceding H2 become the offer name). So editing the visible content updates the structured data — keep the price-in-bold table convention. `/llms.txt` and `/en/llms.txt` (`src/lib/llms.ts`) are generated from `business_info` + the indexable pages (`src/lib/page-index.ts`, shared with the sitemap). `palvelut`/`hinnasto` carry a `marketing.faq` block (Usein kysyttyä) added in seed + live DB — drafts written from facts already on the site; service area confirmed by the client: the whole capital region (Vantaa, Helsinki, Espoo, Kauniainen). The business has no opening hours and no coordinates, so `openingHours`/`geo` are deliberately omitted from the JSON-LD. The footer shows the business's contact details (name, phone, e-mail, Y-tunnus) from `business_info`. Editing a page's content through the API creates a *draft* revision — `POST /_emdash/api/content/pages/{id}/publish` to make it live (seo-panel writes are not revisioned and apply immediately).

**Marketing blocks (`packages/marketing-blocks/`)**: a site-local *native* EmDash plugin that adds six Portable Text block types (`marketing.hero`/`features`/`testimonials`/`pricing`/`faq`/`contact`) to the admin editor's insert menu, themed to this site's tokens (adapted from the emdash repo's marketing theme: `--spacing-*`/`--color-*`/`--radius-*` → `--s-*`/`--c-*`, no shadows/gradients, BEM, `.l-container` supplied by the page rather than nested). Facts worth knowing:
- `plugins: []` in `astro.config.mjs` **rejects a bare `definePlugin()` result** ("has no `entrypoint`") — a plugin must be a descriptor whose `entrypoint` is an importable *package specifier*. So this is a real workspace package linked with `pnpm add link:./packages/marketing-blocks` (raw TS source, no build step — same shape as `@emdash-cms/plugin-forms`). Edits to its files are picked up live; a fresh checkout just needs `pnpm install`.
- Rendering is auto-wired through the descriptor's `componentsEntry` (`marketing-blocks-plugin/astro` exports `blockComponents`), so plain `<PortableText>` in `GenericPage` resolves the blocks — no wrapper component.
- The block editor form is Block Kit: no object-group element (CTAs are flat `primaryCtaLabel`/`primaryCtaUrl`), repeaters are scalar-only, and there is **no media picker inside repeaters** (the Hero's single `media_picker` works; it stores only the file URL — no media id/size/alt).
- The blocks import the site's `Button.astro` by relative path (the one deliberate coupling to the host site). Copy for the pricing badge is an editor-authored field (`badgeLabel`) because block components get no `locale` and can't use `src/i18n`.
- The catch-all's 404 status is set in the **route files** (via `src/lib/pages.ts`), not in `GenericPage.astro`: `Astro.response.status` assigned in a child component silently has no effect (page rendered the 404 body with HTTP 200 until this was caught by curl).
- Don't run `pnpm typecheck` while `pnpm dev` is running — it corrupts `node_modules/.vite` and the dev server starts 500-ing ("file does not exist … deps_ssr"); fix is stopping the server and `rm -rf node_modules/.vite`.

All six routes exist and are wired to real content, in both locales (`/en/` mirrors each fi path — see the i18n section below): `/`, `/palvelut/` (the `palvelut` page entry: dividers + three wide Hero blocks + CTA hero), `/hinnasto/` (the `hinnasto` page entry: H2s + built-in table blocks + terms text), `/galleria/` (the `galleria` page entry: 26 consecutive `image` blocks → a grid), `/ota-yhteytta/` (the `ota-yhteytta` page entry: one `marketing.contact` block — details from `business_info` + the form), `/tietosuoja/` (the `tietosuoja` page entry — plain headings + paragraphs, no dedicated template any more; a draft, flagged in its own first paragraph, needs legal review), `/404`. No `/palvelut/[slug]/` detail pages — each service's body is already full-length inline on `/palvelut/`, so a separate page would just duplicate it; revisit only if content grows enough to justify it. 301s for the three changed old-Webador paths live in `astro.config.mjs`'s `redirects` (framework-native, not EmDash's seed-driven `redirects`/`middleware/redirect` — simpler for a fixed, small set). `LocalBusiness` JSON-LD (with `makesOffer` from the `services` collection) renders site-wide from `BaseLayout`.

Seed reference fields use the seed-local `"$ref:id"` syntax (e.g. `"service": "$ref:svc:pets"`) resolved at apply time — confirmed working by inspecting a seeded testimonial in the admin (resolves to the correct service ULID). Note: the admin renders `reference` fields as a raw ID text input by default, not a picker — cosmetic, data is correct; revisit if a nicer editing widget matters to the client.

`repeater` fields (e.g. `services.bullets`) need `validation.subFields` (not `options.fields`) — each sub-field is `{slug, type, label, required?}`, limited to `string | text | url | number | integer | boolean | datetime | select | image` (no nesting, no portableText/reference inside a repeater item).

## i18n / English locale

Fully bilingual now: every collection and menu has `locale: "en"` + `translationOf: "<fi-id>"` entries in `seed/seed.json` (`business_info` too, despite being mostly locale-invariant facts — only `service_area` actually differs per locale, but a full duplicate entry was simpler than splitting one field out). `/en/` routes are real files under `src/pages/en/`, not a rewrite trick — Astro's directory-based i18n routing needs an actual file per locale per route. To avoid duplicating each page's logic, every route is a two-line wrapper (`src/pages/palvelut/index.astro`, `src/pages/en/palvelut/index.astro`, …) importing a shared component from `src/components/pages/*.astro`, which reads `Astro.currentLocale` itself — works from any file since `Astro.currentLocale` reflects the matched route, not which file rendered it.

**A real, non-obvious bug class found here, worth knowing before adding new locale-aware queries**: `getEmDashCollection`/`getEmDashEntry` only apply the locale fallback chain (`en` → `fi`, per `astro.config.mjs`'s `i18n.fallback`) when you explicitly pass `locale`. Omit it, and the query doesn't return "everything" — it filters for entries with **no** locale value, which happens to include untranslated fi-default entries but silently excludes anything with an explicit `locale: "en"`. Two real instances of this shipped and were only caught by testing the `/en/` pages against real seeded content, not by typecheck or build:
- `PriceTable.astro`'s **inner** `price_items` sub-query (filtered by `where: { group: ... }`) needed its own `locale` — passing it on the outer `price_groups` query wasn't enough, and without it the English pricing page silently rendered two price groups with zero items each.
- (historical: `BaseLayout`'s former `servicesForLd` query and) the former `GalleryGrid`'s `gallery_items` query both had the same gap, fixed pre-emptively even though the visible symptom (duplicate/missing entries) wasn't yet showing for gallery (still empty) — check any *new* `getEmDashCollection`/`getEmDashEntry` call added later for a missing `locale` the same way.

The contact form needed a second, separately-admin-created form (`scripts/contact-form-en.json`, slug `contact`) rather than one translated form — see the "Contact form" section below; `ContactForm.astro` picks the form id from `locale`.

## Contact form (`@emdash-cms/plugin-forms`)

The contact form uses EmDash's official first-party forms plugin (registered in `astro.config.mjs`'s `emdash({ plugins: [...] })`, pinned to `0.2.4`), not a bespoke form + API route. This was a deliberate trade-off the client chose knowingly: submissions land in the admin and email automatically with no external provider/API key, at the cost of the form no longer being reproducible from `seed/seed.json` (the plugin has no seed-file integration — forms live in its own plugin storage, configured only through its admin API) and needing extra work to close accessibility gaps it doesn't cover out of the box.

- **Reproducing the form(s)**: after any fresh reseed (e.g. wiping `.wrangler/state`), run `./scripts/setup-contact-form.sh` against the running dev server — it now creates **two** forms, `scripts/contact-form.json` (fi, slug `yhteydenotto`) and `scripts/contact-form-en.json` (en, slug `contact`). Idempotent-safe to re-run (fails harmlessly on a slug conflict if a form already exists). Edit the JSON files to change fields/settings, then re-run — don't hand-edit either form in the admin UI, or the seed script and the live forms will drift. Two separate forms exist because the plugin has no per-form translation mechanism (a single form's field labels aren't locale-aware); `ContactForm.astro` picks `yhteydenotto` vs `contact` from the `locale` prop.
- **How it's rendered**: `src/components/ContactForm.astro` embeds it via a Portable Text `emdash-form` block (`{ _type: "emdash-form", formId: "yhteydenotto" }`), not a `<Form>` tag — despite one of the plugin's own docblocks suggesting `@emdash-cms/plugin-forms/ui`, that export path doesn't exist in `package.json#exports`; the Portable Text block is the only supported integration point for a plugin at this version. `PortableText` auto-resolves it via the `virtual:emdash/block-components` virtual module — no manual component import needed.
- **Styling**: the plugin's own CSS (`@emdash-cms/plugin-forms/styles`) is never imported. `ContactForm.astro` themes it via a **whole-block `is:global` `<style>`**, not a `:global()`-wrapped selector nested under a scoped one — that nearly shipped broken. Astro's scoping only exempts the exact selector text inside `:global(...)`; every *other* compound selector in the same rule (e.g. a plain `.ec-form-submit` nested under `:global(.contact-form) { }`) still gets Astro's scope attribute appended, which then never matches the plugin's actually-unscoped DOM. Caught this because the submit button rendered with no lamp-accent background at all — verify any future style tweak here the same way (`getComputedStyle` in the browser, not just reading the SCSS).
- **Accessibility gap closed on top of the plugin**: the plugin gives inline per-field errors but not PLAN.md §7's exact spec (error summary at top + focus moved to it, `aria-invalid`). `ContactForm.astro`'s `<script>` adds this independently, reacting only to the native Constraint Validation API (`checkValidity()`) rather than the plugin's internals, so it keeps working across plugin updates. It also sets `form.noValidate = true` once JS runs — the no-JS baseline relies on native browser validation (still reasonably accessible on its own); JS takes over so the `submit` event actually fires and custom UI can render instead of the browser's native popup.
- **Two real bugs found and worked around** (both in the plugin's own template/client script, not ours — safe to remove the workarounds on a version bump if fixed upstream):
  1. `FormEmbed.astro`'s `<textarea>` renders `{field.defaultValue || ""}` as JSX-like children, which leaves stray whitespace (the template's own indentation) as the textarea's initial value. That whitespace satisfies the native `required` constraint even when the visitor typed nothing — `checkValidity()` alone says valid. Server-side `validateSubmission` correctly `.trim()`s and would reject it, so a blank message was never going to actually reach Minna, but the client silently let a broken-feeling submit through. Worked around in `ContactForm.astro`'s script with an explicit `value.trim() === ""` check layered on top of `checkValidity()`.
  2. The plugin's client script restores the submit button's label from `form.dataset.submitLabel` after a submission, but its own server template never sets that dataset attribute — so the button silently reverted to the hardcoded English "Submit" after every submit, regardless of locale. Worked around by populating `form.dataset.submitLabel` ourselves from the button's actual server-rendered (localized) text, in the same `<script>`.
- **Retention**: `retentionDays: 0` in `scripts/contact-form.json` means submissions are kept indefinitely (not auto-deleted) — worth revisiting for a tighter GDPR posture (e.g. 365 days), adjustable via the admin's form settings or by editing the script and recreating the form.

## Visual character

Defined — see [docs/design-tokens.md](docs/design-tokens.md) and `src/styles/abstracts/_tokens.scss`. A Nordic winter-dusk palette (not cream/serif/terracotta), Bricolage Grotesque (display) + Atkinson Hyperlegible Next (body), fluid type scale, one CSS-only "lamp glow" signature element. Don't introduce new colours, type sizes, or spacing values outside the token set — extend the tokens instead.

The lamp glow appears in exactly two places per the design brief (the page-opening hero's media area, service-card/Features-card icon on hover) plus one functional exception: the Hero block's icon-glyph fallback (used when a `wide`-shape hero has an icon but no picture) carries an ambient version of it, because that glow is standing in for a missing photo ("use a CSS/SVG visual rather than a grey box"), not decoration for its own sake. The glow is never drawn over an actual picture (no glow when an image is set). A third occurrence on a contact band was added during Phase 3 and removed during Phase 7's self-critique pass — it wasn't in the brief and diluted "the one bold move." If you're tempted to add the glow somewhere else, ask whether it's replacing an actual missing image first.

## Motion

Three sanctioned moments (PLAN.md §2), all wrapped in `@media (prefers-reduced-motion: no-preference)`: the page-opening Hero block's staggered load reveal (`packages/marketing-blocks/src/astro/Hero.astro`, the h1 hero), the hover lamp glow (Features cards with a link), and a scroll-triggered fade-up on a Features block's card grid (`ScrollReveal.astro`, included once from `BaseLayout`). The reveal follows the same no-JS-safe pattern as the mobile nav: elements marked `[data-reveal]` are visible by default, and only get the hide-then-reveal treatment under `html.js` (set by the same bootstrap script the mobile nav uses) — so a visitor without JS, or with reduced motion, always just sees the content. Mark a group's children with `[data-reveal-group] > *` for the staggered `:nth-child` delays.

Print stylesheet lives in `src/styles/base/_print.scss` (hides header/footer/CTAs/decorative glows, forces black-on-white, keeps price rows from breaking across a page) — the price list (`/hinnasto/`) is the primary target per PLAN.md §7, but the rules apply site-wide.

**Tooling note for future screenshot-based review**: the Browser pane's screenshot tool has a rendering quirk in this environment — at some explicit `width`/`height` combinations (observed at 768×900) it captures a devicePixelRatio-scaled but uncropped-to-fit image, making a fully-correct layout look cut off at roughly half width. Verified this is a capture artifact, not a real bug, via `getComputedStyle`/`getBoundingClientRect` (grid columns summed to the full requested width) — the `tablet`/`mobile` presets and explicit widths like 320 or 1280 rendered correctly. If a screenshot at some other specific width looks implausibly broken (content cut off mid-container with a large flat blank area, not a wrapping/overflow issue), cross-check computed styles before concluding it's a real layout bug.

## QA (Phase 8)

Full results in [README.md](README.md#qa-results). Three real bugs found and fixed via actual tooling (axe-core, Lighthouse, W3C Nu validator), not just re-reading the code:

- `PriceTable`'s group headings were `<h3>` directly under each page's `<h1>` (skipping `<h2>`) — axe caught this as `heading-order` on `/hinnasto/` specifically (other pages happened to have an `<h2>` in between). Now `<h2>`.
- No favicon existed — Lighthouse's `errors-in-console` audit caught the resulting `/favicon.ico` 404. Added `public/favicon.svg` (a simple paw mark in the token palette, referenced from `BaseLayout`) rather than letting the browser fall back to the unstyled default.
- `BaseLayout` and EmDash's own `<EmDashHead>` were both rendering `<meta name="description">` from the same value — the W3C validator flags duplicate description tags as an error. Removed ours; `<EmDashHead>` already covers it (and og:/twitter: description too).

When installing `axe-core` or similar testing-only tools to run browser-side checks, they went in as a `devDependency` and any temp file used to inject them into the page (e.g. copying `axe.min.js` into `public/` so a `<script src>` could load it) was deleted again afterward — don't leave test-only assets in `public/`.
